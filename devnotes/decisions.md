# Decisions

- Use UserGuid, ShowGuid, SeatGuid, ReservationGuid for public identifiers; internal BIGINT IDs remain for relationships and locking.
- Per-user booking limit is 4 by default.
- Multi-seat reservation semantics are all-or-nothing.
- Release model is explicit owner-only cancellation.
- MySQL/InnoDB is the source of truth.
- Reservation correctness uses one transaction, user-row serialization for per-user/idempotency races, and deterministic seat-number locking.
- Idempotency is persisted on Reservations with a request hash and unique (UserId, IdempotencyKey).
- Temporary tables are used for multi-seat stored-procedure inputs and created/populated on the same MySQL connection used to call the procedure.
- Stored procedure names and temporary table names are centralized in constants.
- No EF Core.
- Money is integer paise.
- No Services folder; assignment application logic is kept in Helpers.
- Database infrastructure is kept in Utility/Database.
- JWT infrastructure is kept in Utility/Authentication.
- Configuration secrets are provided through environment variables, not committed in appsettings.json.
- Stored procedures are one file per procedure under database/functions.
- Future schema changes use timestamped files under database/migrations and are never edited after application.
- Stored procedures use set-based SQL and no cursors.
- Reservation locking uses SELECT ... FOR UPDATE over the requested seats in a deterministic seat-number order; the API consumes that internal result set before reading the procedure outcome.
- No separate automated test project has been added yet; manual API validation will be performed against the running Docker service first.
